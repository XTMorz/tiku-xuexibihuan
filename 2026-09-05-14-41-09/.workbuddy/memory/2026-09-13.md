## 完成：跨设备同步（GitHub Gist）

用户想跨设备保持相同的题库记录，最终选择用 GitHub Gist 作后端（夸克网盘不支持原生 WebDAV，坚果云方案被排除）。

改动文件：
- `index.html`：加「同步设置」入口、header 同步状态条、新的 `modal-sync`（含 Token/Gist ID/设备名/自动同步/手动拉取上传）
- `app.js`：新增 Gist API 封装（test/create/get/update）、Payload 构建与合并、自动同步 debounce（答题 5 秒后上传）、启动自动拉取、冲突弹窗确认
- `styles.css`：`.sync-indicator`、`.sync-status`、`.field`、`.checkbox`、`.sync-actions` 等同步相关样式
- `vendor/icons.js`：新增 `sync` 图标

用户操作路径：
1. 设置 → 同步设置
2. 在 GitHub 创建 Fine-grained Token（仅勾选 Gists: Read and write）
3. 填 Token → 点「创建 Gist」自动生成 Gist ID
4. 另一台设备填同一个 Token + Gist ID → 开「自动同步」即可共用数据

限制：
- GitHub Gist 单文件大小限制 1MB（题库 JSON 通常几十 KB）
- 浏览器 fetch 受 CORS 影响，GitHub REST API 已支持 CORS，无需后端
- Token 明文存在本地 localStorage（符合本地优先设计）

## Bug 修复：popover 内「同步设置」点击无反应

`settingsPopover` 的统一 click handler（`app.js` line ~2842）在 if/else 链里漏了 `action === 'sync'` 分支。原本指望 `initSync()` 里 line ~2653 单独绑的 listener 兜底，但 initSync 调用在 popover listener 之后（`init()` 函数末尾 line ~2901），若中间任一事件绑定抛错，sync listener 会漏绑，结果点同步设置就完全没反应。

修复：在 popover handler 里加上 `if (action === 'sync') { openSyncModal(); }`，独立 popover listener 就能直接处理，不再依赖 initSync。

教训：**所有 popover-item 的 action 必须在统一 handler 里全部覆盖**，不能依赖分散在各 init 函数里的子 listener 兜底。

## 完成：解析器修复 + 题型显示 + 计算分析题文字作答

### Bug 1：解析器第 6 题以后漏关联答案/解析（用户报告）

**根因**：`parseAnswerBlock` 的表头跳过正则 `/^(题\s*号|答\s*案|解\s*析|题目|答案|解析|题号|参考答案.*?及.*?解析)/` 没有 `$` 结尾，把「解析1」「解析2」「解析6」这种含答案/解析的行都当成表头跳过了！并且没要求独立成行，导致 PDF/Word 答案区常见格式识别失败。

**修复**：
1. 表头正则加 `$` 结尾 + `i` flag → `/^(题\s*号|答\s*案|解\s*析|题目|答案|题号|参考答案.*?及.*?解析)\s*$/i`
2. 增加「数字+标点」前缀识别：`/^(\d+)\s*[\.\、\:\u3000]\s*(.*)$/` 支持「6.」「6、」「6:」「6、」
3. 增加「第N题 xxx」行内格式：`/^第\s*(\d+)\s*题\s*[:：\.\、\s]?\s*(.*)$/`
4. 增加 tab 分隔支持：`split(/\t+/)` 检测「题号\t答案字母\t解析」三栏
5. 答案字母行支持「B 解析...」一行式（增强原正则 `/^[A-H](?:[\s,、]+[A-H])*\s*(.*)$/i`）
6. 新增 `matchAnswerToken(s)` 工具函数提取本行「答案+剩余文字」

### Bug 2：第 6 题后答案区格式变化（用户报告「6 题以后全断」）

最常见根因：答案区「第 6 题起切换到综合题/计算分析题」段落式，但旧 parser 不识别「第N题」+ 后续多行。修复同上，新解析器已覆盖。

### 单元测试覆盖

## 完成：解析器第二次修复（calc/essay 答案区「第N题」 curType 错切 bug）

### Bug 复现
首轮修完后，仍有 56 个 calc 题的答案/解析为空，集中在第五章 / 第八章 / 第十三章 / 第十四章 / 第十七章 / 第十八章 / 专题一 Q6。trace 显示这些章节的答案区都有「四、计算分析题」+「第N题」+「(1)(2)(3)」结构（第五章为例）。

### 根因
`parseAnswerBlock` 的 `essayHeader`/`essayInline` 在「curType 已经是 calc/essay」的分支里用了
```js
let qRef = qtypes.find(q => q.num === parentNum && q.qtype === curType);
if (!qRef) qRef = qtypes.find(q => q.num === parentNum);   // ← 这里兜底回 single!
if (qRef && qRef.qtype !== curType) curType = qRef.qtype;
```
当章节同时存在 single #1 (qtypes num=1, qtype=single) 和 calc #1001 (num=1001, qtype=calc) 时，「第1题」触发 essayHeader，curType=calc，`qtypes.find(num=1, qtype=calc)` 找不到，兜底返回 single #1，于是 curType 被切成 single，后续 (1)(2)(3) subAnsMatch 全部不进 if 分支，整段答案被丢弃到 cur.explanation 但 cur.num 是 parentNum 1，下次 (1) 进来时又把这个假数据写到 map.calc[1]，真正 1001/1002/1003 全部没内容。

同时 calc 章节里虽然有 subAnsMatch 创建 cur，但每次「(1)」进来前 essayHeader 已经创建了 cur={parentNum, ans:'参见解析', exp:''}，subAnsMatch 第一行又会把这个假 cur 保存到 map.calc[parentNum]（根本没有这个题号），污染数据。

### 修复
- 新增 `findQtypeByParent(parentNum)`：用 `[parentNum*1000, parentNum*1000+1000)` 区间反查 qtypes 真实 qtype，不再用 `num===parentNum` 找。
- `essayHeader` / `essayInline` 第一分支（curType 已经是 calc/essay）信任 curType，只在 `findQtypeByParent` 返回不同 qtype 时切（如 essay 段后接 calc 父题）。
- 第一分支**不再用 parentNum 创建 cur**（`cur = null`），让下一行 (1) subAnsMatch 直接创建 subNum cur，避免 `map[curType][parentNum]` 假数据。
- 第二分支（curType 是 single/multi/judge）改用 `findQtypeByParent`，找不到则默认 'essay'（保留兜底）。

### 改进 UX：calc/essay 参考答案显示
calc/essay 的 `q.answer` 大多是「参见解析」占位符，真正答案在 `explanation` 里。`renderFeedback` 在 answer 是占位符时把 explanation 第一行 200 字提到「参考答案」字段，避免用户看到一行无意义的"参见解析"。
